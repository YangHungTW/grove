## Scope deviation (1) — `src/core/settingsStore.ts`

**Not in the plan's Files Touched. Changed anyway, deliberately.**

The round-trip test failed on first run: `skills` vanished across save/load.
Cause is a pre-existing heuristic at `settingsStore.ts:23-24` — *any* single
-agent array whose entry is `{id:'claude', command:'claude'}` is assumed to be
the legacy auto-created default and is replaced wholesale with
`DEFAULT_SETTINGS.agents`.

For the single most common configuration (Claude only), that silently discards
the user's default skills on every load. The feature would have appeared to
work until the next restart.

Minimal fix applied: the legacy check now also requires `!a[0]?.skills?.length`.
Behaviour is unchanged for every settings file that does not set skills.

Note this heuristic still clobbers *other* customizations (a renamed or
re-iconed lone Claude entry) — a real pre-existing bug, left alone here because
it is unrelated to this plan.

## Scope note (2) — no `src/core/skillsStore.ts`

Discovery would naturally live in an fs-backed sibling module (the
`settings.ts` / `settingsStore.ts` pattern). Acceptance Criterion 1 pins the
discovery test to `src/core/skills.test.ts`, and a new module would itself be
outside Files Touched — so `discoverSkills` takes an injected `SkillFs`
instead, keeping `skills.ts` free of Node builtins so the renderer can import
`withSkills` from it. The ~12-line real adapter lives in `src/main/index.ts`
and is mirrored in the test, so discovery is still exercised against real files.
