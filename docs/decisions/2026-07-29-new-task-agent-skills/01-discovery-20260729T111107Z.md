## The constraint that shapes everything

Verified against the locally installed Claude Code v2.1.220:

- `claude --skill foo` and `claude --skills foo` both fail with
  `error: unknown option`. **No such flag exists.** There is also no
  `claude skills` subcommand.
- The `--agents` JSON *does* have a `skills:` field, but it is documented and
  observed as **subagent-only** — it silently no-ops for the main session agent.
  Confirmed by experiment: preloading via `skills:` left a probe skill's
  passphrase out of context, while `initialPrompt: "/probe"` produced it.
- What *does* work, and is the documented idiomatic path: put `/skill-name` on
  the first line(s) of the initial prompt. Verified for one skill and for two
  stacked skills.

So this feature is **prompt composition**, not flag assembly. That single fact
determines the seam: everything happens before `withInitialPrompt`, inside the
prompt string itself.

`withInitialPrompt` already returns the command **unchanged** for an empty
prompt (`newTask.ts:16`). That is exactly the "no skills selected → inject
nothing" semantics, so the fallback comes free if the composition happens on
the prompt string rather than on the command.

## Chosen injection point

`startTask` (`store.ts:794-806`), *before* `addSession`. Composing there means:

- `addSession`'s already 7-argument positional signature is **not extended** —
  the skills ride inside `initialPrompt`.
- The skill lines pass through the exact same `shellQuote` path as the task
  text, so they inherit the existing `$SHELL -ilc` and tmux re-quoting
  guarantees (`newTask.ts` doc comment; `tmuxLaunch.ts:52-64`).
- Nothing changes for non-New-Task sessions, which have no initial prompt.

## Skill discovery

Precedence per the docs: personal `~/.claude/skills/<name>/SKILL.md`, project
`.claude/skills/<name>/SKILL.md`. **The invocable name is the directory name,
not the frontmatter `name`.** Frontmatter supplies `description` (useful as a
UI hint) and `disable-model-invocation`.

Two options considered:

1. Parse the stream-json `init` message's `skills` array — complete (includes
   plugin/bundled skills) but costs a model turn per dialog open. Rejected:
   far too slow for a dialog, and it would spawn a CLI process.
2. Glob `SKILL.md` under the two directories and read frontmatter — instant,
   no subprocess. **Chosen.** Its known gap is plugin-namespaced skills
   (`/yang-toolkit:dashboard`), which do not live under those paths; the plan
   already scopes those out and the per-agent default field accepts free text,
   so they remain reachable by typing.

## Constraints carried into implementation

- Render the picker as `.dialog-check` checkboxes, **not** a
  `.dialog-field input` — `e2e/smoke.mjs:345-347` takes the *first*
  `.dialog-field input` as the Branch field and would break.
- Tests: `vitest.config.ts` includes only `src/**/*.test.ts`. No `.tsx` tests,
  no React Testing Library — component logic is exercised through `Store`
  (`store.test.ts:110-145`). Pure logic therefore has to live in `src/core`.
- `CCM_AGENT_CMD` short-circuits `launchSpecFor` (`main/index.ts:270-287`), so
  e2e can assert the assembled command string but cannot verify real skill
  loading.
