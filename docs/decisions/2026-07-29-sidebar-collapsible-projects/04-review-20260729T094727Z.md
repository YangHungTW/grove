## Defect found and fixed

**`removeProject` never re-derived the persisted collapsed set.**
`src/renderer/store.ts:716`

`persistCollapsed()`'s stated justification — and the architecture doc's claim —
was that deriving the array from live projects "drops closed projects out
automatically." That was false for the one path that actually closes a project.
`removeProject` deleted from `this.projects` and persisted layout and
closed-agents, but never called `persistCollapsed()`, so the stale root survived
in settings until some *unrelated* toggle happened to re-derive.

Reproduction (single session, no intervening toggle):

1. Collapse project A → `collapsedProjects: ['/path/A']` persisted.
2. Close project A via the X button → `removeProject('/path/A')`. Settings still
   contain `/path/A`.
3. Reopen the same folder via "+ Open project…" → `upsertProject` seeds
   `expanded: !collapsed.includes(repoRoot)` and the freshly-opened project
   starts **collapsed**.

This contradicted the default-expand-on-open behaviour the feature promises. It
is distinct from the trade-off the architecture doc knowingly accepted (stale
entries for projects that never reload in a later session) — this one is
same-session and user-triggered.

**Fix**: `persistCollapsed()` added to `removeProject` after the layout persist,
with a comment naming the reopen symptom. Covered by a new regression test,
`closing a collapsed project drops it from the persisted set, so reopening
starts expanded`, which asserts both the persisted array and that a subsequent
`upsertProject` of the same root comes back expanded. The test failed against
the pre-fix code with the stale root present, and passes after.

Adding it surfaced two missing stubs (`projectRemove`, `closedAgentsSave`) in
the shared `installApi` helper, now added.

## Checked and found correct

- **`init()` ordering** — `persistCollapsed` is unreachable during `init()`
  (only `toggleProjectExpand`, `collapseAll`, `expandAll`, `jumpToPending` call
  it). All projects are upserted before the first `notify()`, so no toggle can
  run against a partially-populated map and wipe legitimate entries.
- **`upsertProject`** — seeds `expanded` only on first creation; existing
  entries only get hooks updated.
- **Deleted force-expand in `setActiveProject`** — verified independently
  against every caller: `cycleProject` (`store.ts:849`), `switchProject`
  (`:834`), `openProject` (`:663`) and `init()` (`:1634`) all just delegate to
  `setActiveProject` and none read `expanded`. `selectWorktree` and
  `cycleWorktree` never depended on it either. A user *can* now have an active
  worktree hidden inside a collapsed group — that is the deliberate, plan-level
  decision (auto-expand was explicitly declined), it is tested, and it is
  reversible with one caret click.
- **`jumpToPending`** — the `expandedOne` guard is correct; `persistCollapsed`
  fires only when a project was actually expanded, not on every jump.
- **Rapid-toggle race** — `SettingsStore.save()` and the `settingsSave` IPC
  handler are fully synchronous (`readFileSync`/`writeFileSync`), and each
  persist sends the complete derived array rather than a delta, so ordered
  `invoke` delivery cannot produce a stale result.
- **React** — `.project-attention` sums `worktreePending` only over the
  project's own worktrees and is gated on `!expanded && attention > 0`.
  Unmounting `.worktrees` drops only presentational state; no store data lives
  there.

No other findings at or above the reporting confidence bar.
