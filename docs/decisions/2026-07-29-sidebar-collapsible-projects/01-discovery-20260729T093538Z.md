## New findings the plan did not have

1. **`upsertProject` initializes `expanded: false`** (`src/renderer/store.ts:636`).
   This is the single most important discovery of the phase. The field defaults
   to *collapsed*, and that was harmless only because nothing read it and
   `setActiveProject` immediately force-set it `true`. Naively gating
   `.worktrees` on `expanded` would ship every project collapsed by default —
   breaking the intended UX **and** the existing e2e assertions.
   → `upsertProject` must seed `expanded` from the persisted collapsed set.

2. **`init()` ordering is favourable.** `this.settings = await
   window.api.settingsLoad()` runs at `src/renderer/store.ts:1573`, *before* the
   `upsertProject` loop at `:1579-1585` and the `projectAdd` upsert at `:1585`.
   So `this.settings.collapsedProjects` is already populated when projects are
   constructed — no second rehydration pass is needed.

3. **`upsertProject` is the only `ProjectView` constructor** in `src/`
   (grep for `expanded` returns only the declaration, the constructor, the three
   mutation sites, and `store.test.ts:38`). One seam to change.

4. **`reconcileWorktrees(project)` is private** (`src/renderer/store.ts:501`)
   but **`reconcileAllWorktrees()` is public** (`:518`). Criterion 3's reconcile
   assertion can call the public one. Reading its body confirms it never touches
   `expanded` — it only add-merges into `project.worktrees` — so collapse state
   should survive the 20s poll by construction. The criterion pins it as a
   regression guard rather than a fix.

5. **`DEFAULT_SETTINGS` is re-exported** from `src/core/settingsStore.ts:5`, and
   `src/core/settingsStore.test.ts` imports it from `./settingsStore` (not
   `./settings`). New assertions there must follow that import.

6. `SettingsStore.load()` (`src/core/settingsStore.ts:26`) spreads
   `DEFAULT_SETTINGS` before parsed content, so a settings file written before
   this feature gains `collapsedProjects: []` for free — no migration code.
